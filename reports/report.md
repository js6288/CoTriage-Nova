> 作品报告初稿

> 版本：V0.1（2026年7月）  
> 说明：本文已完成方案、系统和实验设计部分。所有标注为“待实验”的数据、图表和结论均须在正式提交前用实测结果替换，不应将目标值或预期值作为实验结果。

## 摘要

工业设备、基础软件和边缘节点持续产生海量运行日志。传统关键词和固定规则告警虽然响应快、可解释，但面对日志模板漂移、未知故障和多设备关联异常时容易漏报或误报；将所有日志上传云端大模型又会引入带宽、时延、费用、隐私和弱网不可用等问题。针对上述矛盾，本文设计并实现 CoTriage，一套面向工业多设备日志的云边协同智能故障感知与决策系统。

CoTriage 采用事件驱动的“端侧采集—边缘分层推理—自适应路由—云端深度诊断—反馈学习”架构。边缘侧首先通过规则、模板知识库、MiniLM ONNX 轻量分类器和边缘小语言模型组成的分层推理链完成实时初筛，并输出类别、严重度、置信度、不确定性和证据。随后，本文提出 RAISE（Risk-Aware, uncertainty-calibrated, Intent-constrained, Self-adaptive Edge-cloud routing）路由方法，联合考虑故障风险、预测不确定性、模板新颖度、历史边云分歧、网络状态、队列压力、调用预算和运维策略，在 `LOCAL`、`CLOUD`、`DEFER` 三种动作中在线决策。网络或云服务不可用时，事件先在边缘侧完成基本处置，并通过带优先级的 Outbox 在网络恢复后补传。云端网关聚合相关日志上下文，调用 OpenAI-compatible 大模型生成根因、解释与处置建议，再将纠错和增益反馈给路由器，形成持续自适应闭环。

系统以 Kubernetes、Redis Streams 和 MySQL 为基础，实现了日志采集、可靠流处理、模型与规则热更新、弱网补偿、幂等反馈、可视化监控和一键运行。实验将围绕 BGL、Apache、Linux 和 ZooKeeper 等公开日志，构造工业设备监测与分布式基础设施监测两类场景，与全边缘、全云端、固定置信度阈值和固定级联等方法比较，从端到端时延、F1、云调用比例、通信量、内存占用、弱网业务保持率和决策一致性等方面验证方案。实验数据将在后续实测完成后补入。

**关键词：** 云边协同；工业日志；异常检测；轻量化推理；动态任务调度；弱网自治；大语言模型；AIOps

## 1. 项目背景与问题定义

### 1.1 背景

在工业制造、能源设施、数据中心和智慧城市等场景中，大量设备和服务以日志形式记录运行状态。一方面，告警必须尽可能靠近现场完成，以满足低时延、断网可用和安全生产要求；另一方面，单台设备或单个边缘节点只能观察局部信息，难以完成跨设备关联、复杂根因分析和长文本处置建议生成。

现有方案主要存在三类局限：

1. **纯规则方案泛化能力不足。** 固定日志等级和关键词规则依赖人工经验，难以覆盖未知模板和复杂语义，容易产生漏报与误报。
2. **纯云端方案实时性和经济性不足。** 原始日志全量上传会增加网络流量、云端推理费用和数据泄露风险，网络波动时还可能使核心诊断链路失效。
3. **简单云边级联缺少系统约束。** 仅用固定置信度阈值决定是否上云，无法适应故障爆发、预算变化、队列积压和弱网状态，也难以解释运维策略与学习模型发生冲突时的处理方式。

### 1.2 研究问题

本文关注连续日志流中的在线云边协同决策。对于时刻 \(t\) 到达的事件 \(e_t\)，边缘侧已经给出故障类别、严重度、置信度和推理路径；系统还可以观测网络质量、队列积压、云端健康状态和调用预算。需要在线选择：

- `LOCAL`：采用边缘结果，立即完成本地告警或处置；
- `CLOUD`：立即发送至云端大模型深度诊断；
- `DEFER`：事件值得上云，但当前网络、限流或预算条件不满足，先本地处置并进入待补传队列。

目标是在满足时延、预算、隐私与业务连续性约束的前提下，使高风险和高不确定事件尽可能获得云端复核，同时减少不必要的数据上传和云端调用。

### 1.3 作品目标

CoTriage 面向赛题要求设定以下目标：

1. 在边缘侧完成日志实时采集、预处理、轻量推理与初步决策；
2. 根据任务价值和运行状态动态选择边缘或云端计算路径；
3. 网络波动和云端不可达期间保持基本告警功能，并在恢复后完成高价值事件补传；
4. 通过云端全量模型提升复杂故障根因分析和处置建议质量；
5. 形成可扩展、可配置、可追踪、可复现实验的端到端原型；
6. 在至少两类差异明显的日志监测场景中量化实时性、准确性、资源效率、稳定性和一致性。

## 2. 需求分析与总体方案

### 2.1 功能需求

系统需要覆盖以下完整业务闭环：

- 多节点日志就近采集和统一事件化；
- 边缘规则、模板、轻量模型和小语言模型分层推理；
- 网络、预算、风险和不确定性联合感知；
- `LOCAL/CLOUD/DEFER` 动态路由；
- 弱网缓存、优先补传、重试和死信处理；
- 云端上下文聚合、结构化诊断和反馈写回；
- 规则、模板、边缘模型和云端模型的在线配置；
- 实时事件流、异常态势、路由解释和 Outbox 状态展示。

### 2.2 非功能需求

- **实时性：** 边缘快速路径不依赖云端，避免云端长尾时延阻塞现场告警。
- **可靠性：** Redis 消费采用成功后确认；数据库写入和下游发布具有幂等保护；临时网络错误自动重试。
- **弱网自治：** 网络中断时本地功能继续运行，待上云事件持久化保存。
- **可解释性：** 每次推理保留推理路径和证据，每次路由保留分数、阈值、原因及系统状态快照。
- **可扩展性：** 采集器按节点部署，推理和路由组件可独立扩容，模型通过 HTTP/OpenAI-compatible 接口解耦。
- **安全性：** 上云前对 IP、邮箱、口令、Token、Key 和长十六进制串进行脱敏；运维策略可禁止敏感来源上云。

### 2.3 总体架构

```text
设备/服务日志
    │
    ▼
log-collector（DaemonSet，就近采集）
    │ cotriage.events.raw
    ▼
edge-infer（规则 → 模板 → MiniLM ONNX → 边缘小 LLM → 降级）
    │ cotriage.events.inferred
    ▼
router-controller（RAISE）
    ├──────── LOCAL ────────► 本地结果/告警
    ├──────── CLOUD ────────► cotriage.events.cloud.req
    └──────── DEFER ────────► MySQL cloud_outbox
                                      │ 网络恢复、按优先级补传
                                      ▼
cloud-gateway（上下文聚合、脱敏、云端大模型诊断）
    │ cotriage.events.cloud.resp + cloud_feedback
    ▼
router-controller（反馈更新） + server（统一 API）
    │
    ▼
web（实时大盘、策略与模型管理、路由解释）
```

系统的“边缘”不是单个低算力终端，而是部署在工厂、车间、园区或站点近端的小型 Kubernetes 集群。日志采集、消息队列、轻量推理、路由和控制面均可部署在边缘域内；云端大模型以外部 API 方式按需接入。

## 3. 系统设计与实现

### 3.1 统一事件模型与消息拓扑

系统将一次需要分诊的日志窗口定义为一个 Event，并以 `event_id` 串联全链路。主要状态包括：

```text
CREATED → INFERRED → ROUTED → CLOUD_PROCESSING → CLOUD_DONE → DONE
     └───────────────────────────────异常重试──────────────→ FAILED/DLQ
```

Redis Streams 拓扑如下：

| Stream | 写入组件 | 主要消费组件 | 作用 |
| --- | --- | --- | --- |
| `cotriage.events.raw` | log-collector | edge-infer | 原始日志事件 |
| `cotriage.events.inferred` | edge-infer | router-controller | 边缘推理结果 |
| `cotriage.events.routed` | router-controller | server/web | 路由决策与解释 |
| `cotriage.events.cloud.req` | router-controller / outbox replayer | cloud-gateway | 云端诊断请求 |
| `cotriage.events.cloud.resp` | cloud-gateway | server/router | 云端诊断结果 |
| `cotriage.events.dlq` | 各处理阶段 | 运维人员/server | 不可恢复错误 |

各消费者仅在当前阶段成功落库并完成下游发布后确认消息。`event_id` 和 `idempotency_key` 用于防止重复消费产生重复计费或重复反馈。

### 3.2 日志采集：log-collector

`log-collector` 以 DaemonSet 运行在边缘集群工作节点上，从指定日志文件或容器日志来源持续采集数据。采集器将相邻日志按时间窗口聚合，补充节点、设备、时间范围和来源信息，再写入原始事件流。该设计实现了：

- 数据在设备近端完成初步规整，减少后续重复解析；
- 每个节点独立采集，新增节点时自动扩展；
- 通过 `event_id` 和来源字段支持多设备关联与全链路追踪；
- 日志重放器可以用公开数据集模拟不同设备和不同负载。

### 3.3 边缘分层推理：edge-infer

边缘推理采用由快到慢、由确定到开放的五级路径：

1. **规则路径。** 对明确的严重级别、关键词和运维规则快速判断，具有最低时延和较强可解释性。
2. **模板路径。** 使用管理端发布的模板知识库和 Redis 临时模板缓存复用历史判断。
3. **轻量分类模型路径。** 使用 MiniLM 二分类模型识别 `NON_ALERT/ALERT`，导出为 ONNX 后通过本地 HTTP 服务调用。
4. **边缘小语言模型路径。** 对分类器判定为异常的日志进一步识别 `APP_ERROR`、`NET_ERROR`、`DISK_ERROR`、`INFRA_ERROR`、`SECURITY` 等细分类。
5. **降级路径。** 模型不可用、超时或未命中时输出 `FALLBACK/UNKNOWN`，保证流水线继续运行，并由路由器决定是否上云。

每条结果包含：

```text
edge_pred, severity, confidence, uncertainty,
inference_path, evidence, model_version, latency_ms
```

规则、模板和模型配置由 Server 统一发布。edge-infer 使用 ETag 轮询配置，配置有效时原子替换；拉取失败或新配置校验失败时继续使用上一份可用配置，因此控制面故障不会立即破坏数据面。

### 3.4 轻量模型训练与部署

当前边缘分类器基于公开 BGL 日志数据训练。预处理阶段从原始标签构造 `NON_ALERT/ALERT` 二分类任务，对日志消息进行模板归一化，并以 `template_id` 为单位进行确定性训练集、验证集和测试集划分，避免同一模板同时出现在训练集和测试集造成数据泄漏。纯度不足的歧义模板单独保存，不用于主训练集。

主模型采用 `all-MiniLM-L6-v2`，输入形式为：

```text
<component> <level> <normalized message template>
```

训练完成后导出 ONNX 模型、Tokenizer、阈值和标签映射，由 ONNX Runtime 提供本地推理服务。DistilBERT 作为较大模型对照组，用于研究边缘资源占用和准确率之间的权衡。当前小规模模板级结果仅用于功能验证，正式报告中的模型效果必须基于扩充后的事件级测试集和跨数据集测试。

### 3.5 自适应路由：RAISE

RAISE 将云边路由建模为风险收益和系统成本共同约束的在线决策。其核心分数为：

```text
S_t = β_v V(e_t) + β_g G(e_t) - β_k K(e_t, s_t)
```

其中：

- \(V(e_t)\) 表示事件的上云价值，由严重度、不确定性、模板新颖度、历史边云分歧、影响设备范围和推理路径风险组成；
- \(G(e_t)\) 表示云端可能纠错或补充有效信息的边际收益；
- \(K(e_t,s_t)\) 表示云调用、时延、网络、队列、预算和隐私成本。

动态阈值为：

```text
Θ_t = Θ_0 + α_q Q_t + α_b B_t + α_n N_t - α_a A_t
```

其中 \(Q_t\) 为队列压力，\(B_t\) 为预算压力，\(N_t\) 为网络压力，\(A_t\) 为审计采样不足程度。云端越拥塞、预算越紧或网络越差，阈值越高；近期上云样本不足时，系统适当降低阈值以保留探索和审计样本。

最终决策为：

```text
LOCAL：S_t < Θ_t
CLOUD：S_t ≥ Θ_t 且网络、健康、预算和限流条件允许
DEFER：S_t ≥ Θ_t 但当前不可发送
```

运维人员的 `deny-cloud`、`force-local`、`force-cloud` 等规则是硬约束，优先于学习分数，防止学习模型覆盖隐私和安全策略。

### 3.6 在线反馈与自适应

云端诊断返回后，系统根据云边结果构造反馈：

| 反馈情况 | Reward |
| --- | ---: |
| 云端纠正边缘错误 | 1.0 |
| 云端增加可执行根因或建议 | 0.7 |
| 云端确认高风险判断 | 0.3 |
| 云端没有增加有效信息 | 0.0 |

router-controller 使用轻量在线收益模型维护不同模板和不同推理路径的上云收益，并加入 UCB 探索项，避免系统只重复选择已知模板而忽略新模板。在线状态可序列化到 MySQL 快照，进程重启后恢复。

### 3.7 弱网自治与最终一致性

当事件值得上云但网络不可用时，RAISE 输出 `DEFER`。事件持久化到 `cloud_outbox`，主要字段包括负载、优先级、截止时间、尝试次数、状态和推迟原因。补传优先级综合考虑严重度、不确定性、预期收益、等待时间和强制上云标记，不采用简单 FIFO。

Outbox 状态机为：

```text
PENDING → SENDING → SENT → DONE
              └──→ RETRY
              └──→ DLQ
```

多实例通过条件更新抢占任务；进程异常退出后，超时锁会被回收；发布失败采用指数退避，超过最大次数进入 DLQ。弱网期间，边缘规则、模板和轻量模型仍可完成本地告警，因此云端故障不会使基本业务停摆。

### 3.8 云端深度诊断：cloud-gateway

cloud-gateway 消费上云请求，从近期边缘事件流中按时间、模板、来源、设备、类别和严重度选择相关上下文，并按 Token 预算裁剪。上云前执行敏感信息脱敏，然后调用 Server 下发的 OpenAI-compatible Provider。

云端模型输出包括：

```text
cloud_pred, root_cause, recommendation,
explanation, confidence, token_usage, latency_ms
```

组件支持结构化 JSON 直接解析、文本中 JSON 对象提取和非结构化响应降级；能够区分超时、限流、服务端错误和配置缺失。反馈先幂等写入 MySQL，再发布响应 Stream，最后确认请求消息；如果数据库已经写入但响应发布失败，重试时直接读取已保存结果补发，避免再次调用大模型。

### 3.9 Server 与 Web 控制面

Server 提供设备、事件、异常态势、路由决策、Outbox、规则、模板、边缘模型和云端模型的统一 REST/SSE API。Web 管理端实现：

- 实时日志分诊大盘和实时事件流；
- 异常类别、设备、模板和推理路径统计；
- RAISE 的 `LOCAL/CLOUD/DEFER` 分布、分数、阈值和原因展示；
- Outbox 状态、补传优先级和重试次数展示；
- 规则、模板知识库、边缘模型和云端模型管理；
- 活动配置发布及 edge-infer 热更新；
- 可选的运维值守数字人交互展示。

数字人属于演示增强功能，不参与核心云边协同指标，也不影响主系统独立运行。

## 4. 关键创新点

### 4.1 面向工业日志的多层边缘推理

系统不是在“规则”和“大模型”之间二选一，而是将规则、模板记忆、轻量分类器和边缘小语言模型按成本分层组合。确定性事件优先走快速路径，开放性问题才逐步升级，使边缘实时性、可解释性和语义泛化能力可以兼顾。

### 4.2 风险、收益与成本统一的三动作路由

RAISE 不仅使用模型置信度，还引入严重度、模板新颖度、历史边云分歧、影响范围、预算、网络和队列状态；`DEFER` 被设计为与 `LOCAL/CLOUD` 同等重要的动作，使“值得上云”和“当前能否上云”解耦。

### 4.3 运维意图硬约束

隐私、安全和生产策略以硬约束覆盖学习结果。该机制既避免黑盒模型越权，也使每次决策可以被运维人员解释和审计，适合工业系统落地。

### 4.4 云端反馈驱动的持续自适应

系统将云端是否纠错、是否给出新根因和是否提供可执行建议转化为 Reward，在线更新模板分歧率和云端边际收益，使路由策略可以随日志分布和模型能力变化调整。

### 4.5 弱网条件下的高风险优先补偿

Outbox 同时提供持久化、抢占锁、超时回收、指数退避和优先补传。网络恢复后，高风险、高不确定和等待时间长的事件优先进入云端，避免普通 FIFO 延误关键故障。

## 5. 典型应用场景

### 5.1 场景一：工业设备与生产服务故障监测

不同生产设备和业务服务持续产生系统日志、应用日志和告警。边缘集群在车间或厂区就近部署：

- `FATAL`、磁盘满、服务崩溃等明确高风险事件由规则或模板快速告警；
- 常见正常日志由轻量分类器留在边缘，减少上传；
- 新模板、低置信或跨设备扩散的异常由 RAISE 送往云端；
- 云端结合时间窗口内多设备日志定位共同根因，生成停机检查、磁盘清理、网络隔离或服务重启建议。

该场景重点验证低时延、高风险召回和网络中断期间的业务连续性。

### 5.2 场景二：分布式基础设施与集群运行监测

ZooKeeper、Web 服务和计算集群等分布式系统通常具有多节点、关联调用和模板漂移特征。单节点日志可能只是局部症状，云端需要综合多个节点的时间邻近事件：

- 边缘侧快速识别节点级异常并维持本地告警；
- RAISE 对新模板、多节点同时异常和历史高分歧模板提高上云优先级；
- 云端根据关联日志区分单节点故障、网络分区、依赖服务异常和集群级故障；
- 网络恢复后，系统优先补传影响范围大的事件。

该场景重点验证多节点关联诊断、模板漂移适应性和决策一致性。

### 6.5 指标定义

1. **感知与决策效果：** Accuracy、Precision、Recall、F1、Macro-F1、高严重度漏报率、边云分歧捕获率、根因 Top-1 准确率或人工评分。
2. **实时性：** 边缘推理时延、路由时延、端到端 P50/P95/P99、云端 TTFT。
3. **资源效率：** 边缘进程峰值 RSS、CPU 使用率、模型文件大小、吞吐量。
4. **通信与费用：** 上云事件比例、上传字节数、带宽占用、云端 Token 数和估算费用。
5. **稳定性：** 弱网期间成功处理比例、基本业务功能保持率、失败率、性能波动范围。
6. **一致性：** 多节点冲突率、冲突解决成功率、Outbox 最终补传成功率、恢复时间。
7. **校准质量：** ECE、Brier Score 和可靠性图。

关键计算口径：

```text
时延降低率 = (基线时延 - CoTriage 时延) / 基线时延 × 100%
通信降低率 = (全云上传量 - CoTriage 上传量) / 全云上传量 × 100%
基本业务功能保持率 = 弱网期间成功产生本地有效决策的事件数 / 弱网期间事件总数
冲突率 = 关联任务中产生不一致决策的次数 / 关联任务总数
冲突解决成功率 = 最终被统一或正确纠正的冲突数 / 冲突总数
```

## 8. 系统可靠性与安全性

### 8.1 消息可靠性

- Redis Consumer Group 支持多消费者协作；
- 处理成功后才 ACK，失败消息保留或进入 DLQ；
- edge-infer 和 cloud-gateway 对 Redis 暂时不可达进行退避重试；
- Stream 定期裁剪，避免长时间运行耗尽 Redis 内存；
- Event 和云端请求使用幂等键减少重复处理。

### 8.2 数据持久化

- 路由决策、Outbox、云端反馈和状态快照写入 MySQL；
- Outbox 通过 CAS 抢占和超时锁回收支持进程故障恢复；
- 云端反馈先落库后发布，避免响应发布失败导致重复调用；
- 配置使用版本号和 ETag 发布，数据面保留上一份可用配置。

### 8.3 隐私和访问边界

- 原始日志默认在边缘域内处理；
- 只有 RAISE 选中的事件和裁剪后的相关上下文上云；
- 上云前进行敏感字段脱敏；
- `deny-cloud` 等硬策略可以禁止指定来源或模板上云；
- Demo 当前允许在管理页面配置云端 API Key，正式生产部署需要接入密钥管理系统并限制明文展示。

## 10. 应用价值与推广前景

CoTriage 的日志事件抽象、分层推理和自适应路由不依赖特定设备协议，可扩展到：

- 工业生产线设备状态监测与风险预警；
- 电力、能源和基础设施站点的边缘自治运维；
- 数据中心、数据库和分布式中间件的 AIOps；
- 智慧城市多站点运行日志和告警协同；
- 对隐私、带宽、时延和离线能力有约束的其他智能感知任务。

系统采用开源通用组件和标准 HTTP/Redis 接口，模型、日志来源、路由权重和云端 Provider 均可替换。新增边缘节点时，采集器可随节点扩展；新增应用场景时，可通过规则、模板知识库和少量领域数据完成适配，而无需重写完整链路。

## 11. 局限性与后续工作

当前原型仍有以下边界：

1. 第一版 MiniLM 训练集的模板样本规模较小，需要增加事件级、时间切分和跨数据集评估；
2. 云端诊断质量需要建立人工标注规范或专家评分流程；
3. router-controller 当前主要按单实例维护在线状态，多副本部署需要进一步引入状态分片或 Leader Election；
4. cloud-gateway 还可补充 Pending 自动接管、Provider 健康探测、QPS 限流和事务型响应 Outbox；
5. 当前 API Key 管理按比赛 Demo 需求简化，生产应用应使用专用密钥管理服务；
6. 决策冲突的定义、关联任务构造和解决标准需要在正式实验前冻结；
7. 赛题要求的边缘模型能力保持率、TTFT、内存、0.2 秒端到端时延、弱网保持率和一致性指标尚待系统化实测。

后续工作将以第 6 章实验方案为主线，优先完成模型基准、端到端基准、弱网实验和一致性实验，再进行 RAISE 消融和参数敏感性分析。

## 12. 结论

本文面向工业多设备日志的实时感知和复杂故障诊断需求，设计并实现了 CoTriage 云边协同系统。系统通过分层边缘推理减少无价值上云，通过 RAISE 在风险、收益、网络、预算和策略约束之间进行在线权衡，通过 `DEFER + Outbox` 在弱网下保持本地自治与最终补偿，并利用云端反馈持续更新路由收益。与仅依赖固定规则、固定阈值或全量上云的方案相比，CoTriage 在架构上形成了从感知、推理、调度、诊断到反馈的完整闭环。

目前系统主链路和管理端已基本开发完成，下一阶段将按照统一实验口径补充量化结果，重点验证其在实时性、感知与决策效果、资源与通信效率、弱网稳定性和多节点一致性方面的表现。
