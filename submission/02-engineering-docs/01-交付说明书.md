## 1. 文档目的

本文档说明 CoTriage 当前可交付的软件组成、运行依赖、配置边界、验收方法和已知限制，供项目交接、评审材料核对和后续部署使用。本文档描述的是上述代码基线中的实际实现，不把设计目标、配置阈值或历史开发记录视为当前实测结果。

本交付包不包含参赛申报表、演示视频成片、队友服务器凭据、真实 API Key、真实组网地址、原始实验服务器快照或未脱敏日志。实验结果和运行截图由开发与实验负责人按证据交接规范另行提供。

## 2. 交付范围

### 2.1 核心软件组件

| 组件 | 代码位置 | 当前职责 | 主要依赖/接口 |
| --- | --- | --- | --- |
| `log-collector` | `log-collector/` | 以工作节点为采集单元，从指定日志文件尾部读取新增日志行，为每行生成 `event_id` 并写入原始事件流 | Kubernetes API、Redis Streams |
| `edge-infer` | `edge-infer/` | 执行日志规范化、规则、模板缓存、MiniLM ONNX HTTP 分类器、可选边缘小语言模型和降级推理 | Redis Streams、HTTP 模型接口、Server 配置接口 |
| `router-controller` | `router-controller/` | 执行 RAISE 路由，输出 `LOCAL`、`CLOUD` 或 `DEFER`，维护运行状态、Outbox 到期重放，并从 MySQL 处理云端反馈 | Redis Streams、MySQL |
| `cloud-gateway` | `cloud-gateway/` | 消费上云请求、聚合上下文、调用 OpenAI-compatible 模型、写入 MySQL 云端反馈并发布响应；响应 Stream 当前无核心内容消费者 | Redis Streams、MySQL、Server 配置接口、外部模型 API |
| `server` | `server/` | 提供设备、事件、大盘、路由、规则、模板及模型配置的 REST/SSE 控制面 | Kubernetes API、Redis、MySQL |
| `web` | `web/` | 提供首页、实时分诊大盘、设备管理、规则管理、模板知识库和模型管理 | Vue 3、Vite、Ant Design Vue、ECharts、Server API |
| MiniLM ONNX 分类器 | `dataset/model-training/` | 将日志模板进行 `NON_ALERT/ALERT` 二分类并通过 HTTP `/predict` 提供推理 | Python、ONNX Runtime、Tokenizer |

数字人相关代码位于 `platform-integrations/`，属于可选演示增强能力，不参与核心云边协同链路，也不作为核心验收的前置条件。

## 3. 软件与环境要求

### 3.1 已由仓库声明的技术基线

- 五个核心 Go 模块（`log-collector`、`edge-infer`、`router-controller`、`cloud-gateway`、`server`）的 `go.mod` 均声明 Go 1.22；
- Web 使用 Node.js 包管理环境，构建入口定义于 `web/package.json`；
- 边缘分类模型服务使用 Python 与 ONNX Runtime，依赖及导出方式见 `dataset/model-training/`；
- 事件流使用 Redis Streams，状态与反馈持久化使用 MySQL；
- 工作节点发现、采集器部署和基础设施运行依赖 Kubernetes；
- 根启动脚本是 Bash 脚本，并检查 `kubectl`、`nc`、`go`，启用 Web 时检查 `npm`，启用数字人时检查 `uv`。

具体操作系统、Kubernetes、Redis、MySQL、Python、Node.js 和硬件版本必须以最终运行环境清单为准：`【待证据：EVID-EXP-ENV-01】`。

### 3.2 配置与凭据边界

运行配置通过环境变量、Kubernetes Secret、控制面配置或本地未跟踪的 `.env` 文件注入。交付和验收时遵循以下约束：

- 不在仓库、本文档、命令历史、截图或日志中写入真实 API Key、密码、Token、kubeconfig 内容或私有组网地址；
- 配置示例只能使用变量名和占位符，真实值由部署负责人在目标环境中注入；
- 截图前检查浏览器表单、开发者工具、终端和系统通知，确保没有敏感信息；
- 当前云端 Provider 的 Demo 级代码模型包含凭据字段，且控制面响应路径需要重点复核；在未完成凭据外置、响应脱敏和访问控制之前，不应暴露到不可信网络；

## 5. 启动方式与重要影响

仓库声明的一键入口为：

```bash
./start-cotriage.sh
# 或
make up
```

可用变体为：

```bash
./start-cotriage.sh --no-cloud
./start-cotriage.sh --no-web
./start-cotriage.sh --with-avatar
./start-cotriage.sh --help
```

必须注意：当前根启动脚本不是只读检查。它会检查 Kubernetes 基础设施、对当前命名空间中的 Redis 执行 `FLUSHDB`、重启 `cotriage-log-collector`，随后建立端口转发并启动本地进程。因此：

1. 只能在确认允许清空运行态事件流、消费者组、模板缓存和重试状态后使用；
2. 不得直接针对生产或保存有重要状态的 Redis 执行；
3. 执行前应记录目标集群与命名空间，必要时先完成数据备份；
4. 本文档编写期间未执行该脚本，也未启动服务或实验。

脚本前台运行时，按 `Ctrl-C` 停止其启动的本地进程和端口转发。详细操作、检查和故障定位见《部署与运维说明书》。

## 7. 已知限制与风险

1. `log-collector` 当前从文件末尾读取新增行，不处理日志轮转或 inode 切换；每条新增日志行构成一个事件，不能将设计文档中的窗口聚合描述当作当前实现。
2. `router-controller` 当前按单副本工作模式实现；若扩展为多副本，需要进一步处理在线状态分片或主从协调。
3. `cloud-gateway` 已具备请求消费、诊断、MySQL 反馈持久化与响应发布链路；Server 当前只对 `cloud.resp` 做长度统计，Router 反馈处理器从 MySQL 读取，Web 不展示云端根因、建议或置信度，因此不能把响应发布写成用户可见的完整反馈闭环。历史材料中的 Pending 自动接管、完整指标/心跳和事务型响应 Outbox 等增强项仍需专项复核。
4. 根启动脚本会清空 Redis DB，属于演示/开发环境的状态重置流程，不是生产无损启动流程。
5. 当前云端 Provider 凭据管理和 Server API 访问控制属于 Demo 边界，发布到共享或公网环境前必须加固。
6. Kubernetes 清单尚未覆盖所有组件的统一发布形态；最终部署拓扑和镜像版本需由部署负责人确认。
7. 数字人是可选演示能力，配置或连接失败不应影响核心系统验收。
8. 本批次没有重跑服务、单元测试、端到端测试或正式实验，所有运行与量化结论等待证据交接。
