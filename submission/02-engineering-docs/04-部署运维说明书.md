## 1. 运维目标与边界

本文说明 CoTriage 的当前部署形态、启动条件、配置管理、运行检查、日志定位、备份恢复原则及常见故障。当前仓库提供的是边缘集群基础设施与本地核心进程组合运行路径，不是经过生产加固的一体化发布平台。

本文不记录真实密码、API Key、Token、kubeconfig 内容、私有组网地址或个人账号。命令中的 `<...>` 表示必须由部署负责人按目标环境填写的占位符；任何生产变更都应遵循所在组织的审批和备份流程。

## 2. 当前部署形态

### 2.1 混合开发/演示拓扑

根启动脚本采用以下组合：

- Kubernetes 集群运行 MySQL、Redis、ONNX 分类器和 `log-collector`；
- 本机通过 `kubectl port-forward` 映射 MySQL、Redis 和 ONNX 分类器；
- 本机启动 `server`、`edge-infer`、`router-controller`、可选 `cloud-gateway` 和 Web；
- 可选数字人由独立 Token Server 与 Agent Worker 提供。

这种方式便于联调，但端口转发和本地进程依赖前台脚本生命周期，不应被当作无人值守生产部署。

### 2.2 Kubernetes 资源

仓库 `charts/` 当前包含：

| 资源 | 形态 | 说明 |
| --- | --- | --- |
| `cotriage-log-collector` | DaemonSet + RBAC | 在非控制面工作节点采集日志并读取 Node 标签 |
| Redis | Deployment + Service + ConfigMap | 承载 Streams；配置启用 AOF/RDB，但当前 Deployment 未挂载 Redis PVC |
| MySQL | Deployment + Service + PVC | 存储配置、路由、Outbox 与反馈 |
| ONNX classifier | Deployment + Service | 对外提供 `/healthz` 与 `/predict` |
| `router-controller` | 单副本 Deployment | RAISE 路由、Outbox 和反馈处理 |
| replayer | DaemonSet | 演示/测试日志回放，不是生产日志源 |

`server`、`edge-infer`、`cloud-gateway` 和 `web` 的统一 Kubernetes 清单需按最终交付环境补齐或另行确认；当前静态部署边界归入 `【证据：EVID-OPS-01】`。

## 3. 前置条件

### 3.1 工具与运行环境

使用根启动脚本前确认：

- 在支持 Bash 的环境运行；Windows 原生 PowerShell 不能直接执行 Bash 脚本，应使用团队已验证的 WSL、Git Bash 或 Linux 环境；
- 已安装并可调用 `kubectl`、`nc`、`go` 和 `seq`；
- 启用 Web 时已安装 `npm` 且 `web/node_modules` 已准备；
- 启用数字人时已安装 `uv` 并完成其独立配置；
- kubeconfig 文件存在，当前用户具备读取工作负载、建立端口转发、执行 Redis 命令和重启采集器所需权限；
- 目标命名空间内 MySQL、Redis、ONNX classifier 和 `cotriage-log-collector` 已部署；
- 本地计划使用的端口未被不相关进程占用。

具体软件版本与硬件配置必须记录在环境清单中：`【待证据：EVID-EXP-ENV-01】`。

### 3.2 启动前安全检查

在运行任何会改变状态的脚本前逐项确认：

- [ ] 已确认 kubeconfig 指向正确集群，命名空间正确；
- [ ] 已确认目标 Redis 中的数据允许被清空，或已完成所需备份；
- [ ] 已确认重启 `cotriage-log-collector` 不会影响其他演示或测试；
- [ ] MySQL 与 Redis 的访问参数通过安全方式注入；
- [ ] 云端 Provider 使用专用、限额、可撤销的凭据；
- [ ] 边缘小语言模型和云端模型 Endpoint 已显式配置，不依赖仓库中的环境特定默认值；
- [ ] 日志中不含不允许进入外部模型的敏感字段；
- [ ] 已安排操作者在脚本前台运行期间观察日志并在异常时停止。

## 4. 配置管理

### 4.1 根启动参数

根脚本识别的主要环境变量包括：

| 类别 | 变量 | 用途 |
| --- | --- | --- |
| 集群 | `KUBECONFIG_PATH`、`NAMESPACE` | 选择 kubeconfig 和命名空间 |
| 本地端口 | `MYSQL_LOCAL_PORT`、`REDIS_LOCAL_PORT`、`ONNX_CLASSIFIER_LOCAL_PORT`、`SERVER_LOCAL_PORT`、`WEB_LOCAL_PORT` | 避免端口冲突并建立转发 |
| 启动等待 | `STARTUP_TIMEOUT`、`SERVER_MIGRATION_TIMEOUT`、`SERVER_SEED_TIMEOUT`、`ROUTER_MIGRATION_TIMEOUT` | 控制冷构建和迁移等待时间 |
| 数据库 | `MYSQL_DSN` | Server 与 Router 的 MySQL 连接；包含敏感信息，不得写入公开文件 |
| 边缘模型 | `EDGE_LLM_URL`、`EDGE_LLM_TIMEOUT` | 边缘小语言模型地址和调用超时 |
| 数字人 | `AVATAR_TOKEN_PORT`、相关 `.env` | 可选增强能力配置 |

修改端口时应同时核对 Web 代理、Server 地址、模型 Endpoint 和端口转发，避免只改一侧。

### 4.2 组件级关键变量

- `log-collector`：`LOG_PATH`、`REDIS_ADDR`、`REDIS_STREAM`、`NODE_NAME`、`EQUIPMENT`、`REDIS_STREAM_MAXLEN`；
- `edge-infer`：Redis/Stream、Consumer Group、规则/模板文件、`EDGE_CONFIG_URL`、分类器、边缘小语言模型、超时、重试和 Stream 裁剪参数；
- `router-controller`：Redis/Stream、MySQL、RAISE 权重与阈值、健康探测、预算、限流、Outbox、反馈和状态窗口参数；
- `cloud-gateway`：启用开关、Server 配置地址、Redis/Stream、Consumer Group、并发、上下文预算、模型调用预算和 MySQL；
- `server`：监听地址、Redis/Stream、MySQL、kubeconfig、设备查询限制、命名空间与采集器标签；
- `web`：Server 代理及可选数字人环境变量。

所有跨组件 Stream 名必须成组修改。配置值、配置来源、修改人、变更时间和回滚值应写入变更记录，不依赖终端历史。

### 4.3 凭据处理

1. Kubernetes 基础设施密码优先使用 Secret；
2. 本地敏感变量使用未跟踪的环境文件或受控凭据系统；
3. 不把真实值写进 YAML、Markdown、截图、Issue 或 Git 提交；
4. 当前云端 Provider 控制面存在 Demo 级明文凭据路径，只允许在受控环境使用；
5. 发布前必须完成凭据外置、接口响应脱敏和访问控制复核；
6. 验证凭据是否存在时只记录 `SET/EMPTY`，不打印值。

## 5. 启动与停止

### 5.1 先查看帮助

```bash
./start-cotriage.sh --help
```

该命令用于查看选项。正式启动前还应人工检查脚本中的目标集群、命名空间和环境变量。

### 5.2 一键启动

仓库声明的入口为：

```bash
./start-cotriage.sh
# 或
make up
```

默认流程会：

1. 检查目标命名空间中的 MySQL、Redis、ONNX classifier 和采集器；
2. 等待基础设施可用；
3. 对当前 Redis DB 执行 `FLUSHDB`；
4. 重启 `cotriage-log-collector`；
5. 建立 MySQL、Redis、ONNX classifier 的本地端口转发；
6. 启动 `server`、`edge-infer`、`router-controller`、`cloud-gateway` 和 Web；
7. 将本地进程日志写入 `.runtime/logs`；
8. 持续监控其创建的进程，直至用户中断。

第 3、4 步会改变运行状态。未经第 3.2 节确认不得执行。

### 5.3 运行变体

```bash
./start-cotriage.sh --no-cloud
./start-cotriage.sh --no-web
./start-cotriage.sh --with-avatar
```

- `--no-cloud`：不启动 `cloud-gateway`，适合仅验证边缘与路由链路；
- `--no-web`：不启动 Vite Web；
- `--with-avatar`：额外启动数字人 Token Server 和 Agent Worker；其配置失败不应阻塞核心方案的独立验收。

### 5.4 停止

保持启动脚本在前台，按 `Ctrl-C`。脚本清理其启动的本地进程和端口转发。停止后检查是否仍有遗留进程或监听端口；不要直接终止不属于本次脚本的共享服务。

停止只结束本地进程和脚本持有的转发，不等于删除 Kubernetes 中的 MySQL、Redis、ONNX classifier 或采集器。

## 6. 运行检查

### 6.1 基础设施

Redis 可用性检查使用现有 SOP 中的命令：

```bash
kubectl -n cotriage exec deploy/redis -- redis-cli PING
```

返回 `PONG` 只证明 Redis 服务可响应，不证明事件链路正常。MySQL Pod 和 Service 可按现有 SOP 检查：

```bash
kubectl --kubeconfig kind-host -n cotriage get pod -l app=mysql
kubectl --kubeconfig kind-host -n cotriage get svc mysql
```

如实际 kubeconfig 或命名空间不同，部署负责人必须使用经过确认的值，不能机械复制示例。

ONNX classifier 的现有健康检查为：

```bash
curl http://127.0.0.1:18080/healthz
```

该检查只有在端口转发已建立且本地端口未调整时有效。

### 6.2 事件链路

使用非破坏性 Stream 长度检查观察数据是否流动：

```bash
kubectl -n cotriage exec deploy/redis -- redis-cli XLEN cotriage.events.raw
kubectl -n cotriage exec deploy/redis -- redis-cli XLEN cotriage.events.inferred
kubectl -n cotriage exec deploy/redis -- redis-cli XLEN cotriage.events.dlq
```

还应结合以下事实判断：

- raw 增长：采集器正在产生事件；
- inferred 增长：`edge-infer` 正在发布结果；
- Router 大盘或 `router_decisions` 增长：RAISE 主链路正在处理；
- cloud request 与 response 配对：云端链路正在处理；
- DLQ 或 Pending 持续增长：存在格式、连接、模型或处理能力问题。

不得仅凭某个 Stream 的长度断言“无丢失”或“处理完成”。运行检查截图与结构化记录归入 `【待证据：EVID-UI-01】`。

### 6.3 Server 与 Web

根脚本默认等待 Server 监听并输出本地访问入口。人工验收至少检查：

- 首页可打开，管理端与大盘可导航；
- `/api/v1/dashboard/summary` 返回结构化结果；
- `/api/v1/events/stream` 与 `/api/v1/router/stream` 能建立 SSE 连接；
- 大盘能显示事件和 Router 状态；
- 设备列表、规则、模板和模型管理接口没有未处理错误；
- Router 为 Degraded 时按第 9 节继续检查，不能把空数据视为正常。

页面与 API 状态证据：`【待证据：EVID-UI-01】`。

### 6.4 日志位置

根脚本将本地进程日志写入 `.runtime/logs/<component>.log`，并记录启动与 Redis 清理日志。排障时只截取支持结论的必要片段，先遮蔽凭据、地址、原始业务日志和个人信息。

集群中的 `router-controller` 可使用仓库现有命令观察：

```bash
kubectl --kubeconfig kind-host -n cotriage logs deploy/router-controller -f
```

其他工作负载应按实际资源名查询，不在未核对清单的情况下编造名称。

## 7. Redis 容量与清理

`edge-infer` 默认周期性近似裁剪 raw、inferred 和 DLQ Stream。人工清理优先使用现有 SOP 的 `XTRIM`：

```bash
kubectl -n cotriage exec deploy/redis -- redis-cli XTRIM cotriage.events.raw MAXLEN '~' 100000
kubectl -n cotriage exec deploy/redis -- redis-cli XTRIM cotriage.events.inferred MAXLEN '~' 100000
kubectl -n cotriage exec deploy/redis -- redis-cli XTRIM cotriage.events.dlq MAXLEN '~' 10000
```

人工裁剪前仍需确认保留策略、消费者进度和证据导出。`FLUSHDB` 是最后手段，会同时删除全部 Stream、Consumer Group、模板缓存、幂等键和重试状态。根启动脚本当前自动执行该命令，因此只能用于允许状态重置的开发/演示环境。

## 8. 备份与恢复原则

仓库当前没有统一的自动备份/恢复脚本，因此本文只规定过程，不提供未经验证的命令。

### 8.1 备份对象

- MySQL 数据：规则、模板、模型配置、路由决策、状态快照、Outbox 和云端反馈；
- Redis 状态：需要保留时包含 Stream、Consumer Group 和运行时键；
- Kubernetes 配置：脱敏后的清单、配置版本和 Secret 名称，不导出 Secret 明文到交付包；
- 模型产物：ONNX、Tokenizer、部署元数据、文件校验值和模型版本；
- 实验输入与输出：`experiment-overview.md`、`results.csv`、配置、原始结果和必要日志。

### 8.2 恢复顺序

1. 核对备份版本、Git commit、数据库 schema 和模型版本；
2. 恢复持久化存储；
3. 启动 MySQL、Redis 与模型服务并检查可用性；
4. 启动 Server，确认迁移和配置读取；
5. 启动采集、边缘推理、Router 与 Cloud Gateway；
6. 检查 Consumer Group、Pending、Outbox 和反馈处理状态；
7. 最后启动 Web 并执行端到端验收；
8. 保存恢复记录，不以“页面可打开”作为唯一成功标准。

备份恢复和故障恢复演练统一归入 `【待证据：EVID-EXP-RELIABILITY-01】`。

## 9. 常见故障定位

| 现象 | 优先检查 | 处置原则 |
| --- | --- | --- |
| 启动前检查失败 | kubeconfig、命名空间、工作负载名称与权限 | 不绕过检查启动；先确认目标环境 |
| 本地端口拒绝连接 | 端口转发进程、Pod 重启、本地端口占用 | 重建属于本次操作的转发并同步配置 |
| MySQL 集群域名本机不可解析 | 本地进程是否错误使用集群内 DNS | 本地使用受控端口转发；集群内使用 Service DNS |
| Server 启动卡在迁移/Seed | MySQL 可达性、权限、迁移超时 | 先查日志和 DB 状态，不重复并发启动多个迁移实例 |
| raw 不增长 | 采集器 Pod、日志路径、文件是否有新增行、Node 标签 | 注意当前采集器只读取启动后追加内容，且不处理轮转 |
| inferred 不增长 | `edge-infer`、Consumer Group、输入字段、模型超时 | 查看 Pending 与 DLQ，区分处理慢和坏消息 |
| `FALLBACK` 比例上升 | 分类器/边缘 LLM 配置、远程配置拉取、Endpoint | 保留上一份可用配置，禁止把降级结果包装成模型诊断 |
| Router 显示 Degraded | Router 进程、MySQL 路由表、Server DB 连接 | 空数据是降级保护，不代表主链路正常 |
| 事件只有 `LOCAL` | RAISE 分数/门槛、策略、系统态、云端健康和预算 | 不先改阈值；先记录输入和 reason |
| Outbox 长期积压 | `next_retry_at`、锁、尝试次数、replayer、Redis 请求流发布 | 检查 `PENDING/RETRY/SENDING/SENT/DLQ`；云健康、预算和限流只影响初始路由，不是 replayer 门控；禁止直接删记录 |
| 云端无响应 | 激活 Provider、Cloud Gateway、配置轮询、外部 API、MySQL 反馈和响应发布 | 不打印 API Key；当前 Web 不展示诊断，Server 也不消费 `cloud.resp` 内容，应使用状态码和脱敏记录分阶段定位 |
| SSE 不更新 | Server、反向代理、浏览器连接、Stream 是否有新数据 | REST 与 SSE 分层检查；暂停按钮只影响页面 |
| 数字人失败 | 可选服务和独立配置 | 从核心验收中隔离，不阻塞主系统 |

## 10. 变更、回滚与发布

每次配置或版本变更至少记录：变更目的、Git commit、镜像/模型版本、环境、操作者、时间、变更前后值摘要、验证结果和回滚条件。

- 规则、模板和模型先保存草稿，经复核后发布/激活；
- 同一类模型只保留一个激活配置，回滚时激活经过验证的上一版本；
- RAISE 权重、门槛、预算和网络参数属于联动配置，修改后必须保存完整快照；
- 数据库 schema 迁移前先备份，禁止用删除 PVC 代替排障；
- 发现凭据泄露时立即撤销/轮换，并清理日志、截图和历史材料；
- 发布失败时优先恢复上一可用版本，不在故障窗口中同时改代码、模型和基础设施。

发布与回滚的静态操作边界归入 `【证据：EVID-OPS-01】`；实际故障恢复结果归入 `【待证据：EVID-EXP-RELIABILITY-01】`。
